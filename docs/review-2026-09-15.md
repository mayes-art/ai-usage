## 接手時的狀態

功能面已可運作，`go vet`、`go test -race ./...` 在檢視前即全數通過。
缺的是格式、資源大小、無障礙標籤、測試與文件；以下為實際處理的項目。

## 本次修正

### 1. `internal/service/store.go` 未經 gofmt

`refreshedResets` 欄位直接接在對齊區塊後面，`gofmt -l` 會標記。改為以空行與註解
分隔成獨立的對齊群組，既符合 gofmt，也不會讓整個 struct 被重新對齊。
（工作目錄是 CRLF，容器內 `gofmt -l .` 會標記所有檔案；以 LF 複本比對才有意義。）

### 2. 內嵌的 Antigravity 圖示過大

`ui.html` 內嵌的 Antigravity 圖示是 540 × 540 的 PNG（base64 前 96 KB、解碼後 72 KB），
但實際只顯示在 17 px 見方。整份 `ui.html` 因此從 26 KB 膨脹到 143 KB。
以 10 × 10 box filter 縮到 54 × 54（涵蓋 300% DPI 的 51 px）後為 1.9 KB，
`ui.html` 回到 49 KB。縮圖時先乘上 alpha 再平均，避免透明區域把顏色帶進邊緣。
Claude（.ico 2.4 KB）與 Codex（104 × 104、10 KB）維持原樣。

### 3. 倒數的 `aria-label` 一律被讀成「帳號額度重置倒數」

`updateCountdowns` 對所有 `[data-reset-at]` 套用同一句 `aria-label`，但倒數有三種：
標題的帳號額度重置、詳細資訊的 `reset_label`（可能是「最舊紀錄滑出」）、
以及其他限額的重置。把 `countdownMarkup` 沒有任何呼叫點在用的 `suffix` 參數
改成 `label`，由呼叫點傳入正確名稱，避免螢幕報讀把本機滑出時間念成帳號額度重置
──那正是 `QuotaResetAt` 要避免的混淆。

### 4. 補上 `service` 的測試

原本 `RefreshDueQuotas`、`QuotaCacheInvalidator` 與 `QuotaResetAt` 沒有任何測試。
新增於 `internal/service/store_test.go`（`testStore` 的參數同時放寬為 `Collector`）：

- `TestQuotaResetAtComesOnlyFromReport`：回報重置會進 `QuotaResetAt`；
  純本機滾動視窗只有 `ResetAt` 與「最舊紀錄滑出」，`QuotaResetAt` 必須是 nil。
- `TestRefreshDueQuotasActsOncePerResetBoundary`：重置前不重查；重置後重查一次並套用新額度；
  同一個重置邊界不會重查第二次；下一個重置邊界會再次生效。
- `TestRefreshDueQuotasNeedsReportPreferenceAndHook`：沒有實作 `InvalidateQuotaCache` 的來源
  不會被額外收集；`prefer_reported_limits: false` 時不觸發任何帳號查詢。

已確認這些測試涵蓋的是行為而非實作細節，透過 `ScanOnce` / `RefreshDueQuotas` / `Snapshot` 進出。

## 後續需求：不透明度 75% 與滑入變不透明

接手檢視後，使用者要求把面板改成平常 75% 不透明、滑鼠指標移到面板上時完全不透明、
移開再淡回去。原本寫死的 `128`（50%）改成 `internal/desktop/panel.go` 的具名常數：
`panelOpacityPercent`（75）換算出 `panelAlpha`（191），`panelAlphaHover` 為 255。

需要留意的兩件事：

- `SetLayeredWindowAttributes` 的 `bAlpha` 是**不透明度**，0 全透明、255 全不透明，
  數值越高越不透明。原本的註解寫「50% 透明」在 128 這個值上剛好兩種說法一樣，
  換成其他數值就會誤導，因此改以不透明度描述。
- 分層視窗的 alpha 是整個視窗的屬性，無法只讓某一列變不透明；
  滑入判定因此是整個面板視窗的矩形，而不是單一來源列。

滑入偵測放在既有的 `LockPanelWindows` 迴圈：`GetCursorPos` 取得游標，與 `GetWindowRect`
比對。為了讓滑入滑出跟得上，迴圈改成每 125 ms 一輪，但只有每秒才做完整的樣式校正
（`EnumWindows` 與 `SetWindowPos`），其餘輪次只對上一輪找到的視窗更新不透明度，
避免把 `EnableMenuItem` / `SetWindowPos` 這類呼叫提高到 8 Hz。
同一輪的設定與驗證共用同一個目標值，游標剛好在這中間移動時才不會誤判成套用失敗。

命中判定抽成 `desktop.cursorOverPanel` 這個純函式放在 `panel.go`，
因此 `panel_browser_test.go` 的 `TestPanelOpacityAndHoverBounds` 在 Linux 容器內也跑得到
（Windows 專用檔案的測試不會出現在 `go test ./...` 的 Linux 執行結果裡）。
測試涵蓋常數值、四個邊界（右緣與下緣不算命中）與負座標的第二螢幕。

## 後續需求：玻璃質感與卡片式儀表板

使用者的訴求是「像儀表板一樣簡單呈現用量，又不佔畫面空間，能讓使用者隨意更動擺放位置」，
並選擇 Liquid Glass 三條路中的 A（頁面內的 CSS 玻璃）。
版面先做成水平並排，確認卡片樣式後再依使用者要求改回垂直堆疊；
卡片的樣式與尺寸沿用水平版，只有排列方向與視窗尺寸的算法改變。

### 做得到與做不到

`backdrop-filter` 只採樣頁面自己背景中位於該元素之後的內容，採樣不到桌面。
瀏覽器沙箱沒有任何 API 看得到視窗外面，所以卡片底下糊的是 `body` 自己鋪的漸層，
不是使用者的桌布。真正的桌面模糊需要 DWM 的 Mica / Acrylic，
但那對外部行程持有的 Chromium 視窗無效，而 Chromium 的 client area 又是不透明繪製的。
換 WebView2 才做得到，但那需要 CGo/COM 與 Runtime 相依，違反單一執行檔與零第三方套件的原則。

### 整窗 alpha 與玻璃的分工

`panelOpacityPercent` 由 75 調到 92。`LWA_ALPHA` 是整窗均勻混色，會連文字一起變淡，
跟玻璃要的「背景糊掉、字保持銳利」相反；把透明感交給卡片的 `backdrop-filter`，
視窗本身只留一點，才是 Apple 那種「玻璃是材質」的做法。滑入變不透明的行為保留。

### 尺寸

`panelHeight` 換成 `panelSize`，同時回傳寬與高，`panelBrowserArgs` 因此多收一個 `width` 參數，
Windows 與 macOS 兩邊的呼叫端一起改。

垂直版的寬度固定為 `panelCardWidth`（200）加 `panelSideChrome`（36）；
高度是 `panelTopChrome`（132）加上來源數乘 `panelCardHeight`（116）與卡間的 `panelRowGap`（8），
Cursor 的兩個模型池再加 `panelCursorPools`（52），下限 `panelMinHeight`（260）。
四個來源含 Cursor 為 236 × 672。

水平版預覽時提出的 175 高度沒有採用：那是草圖數字，實際還要算上視窗標題列、面板 header
與 footer，當時實際是 870 × 292。視窗尺寸是鎖定的，寧可寬裕也不要內容被裁掉。

### 版面取捨

200px 寬的卡片放不下原本左右並排的「標題 + 大百分比」，改成標題在上、百分比自己一行。
改回垂直堆疊後卡片寬度不變，所以這個排法沿用。
計量視窗標籤與 Cursor 各池金額從卡面移到詳細資訊，卡面只留儀表板該有的東西；
這兩項都補成 `meta` 的項目，資訊沒有消失。用量那行裁成一行並補 `title`。
展開的卡片加上 `expanded` 類別。水平版用它讓該張卡佔滿整行，垂直版每張卡本來就滿寬，
改成維持亮起的底色，讓使用者一眼看得出哪一張是開著的。
上限表單與診斷文字在 200px 內會換行，仍然可用但偏擠；要放寬只需調 `panelCardWidth`。

玻璃卡片用漸層填色加 `backdrop-filter: blur(22px) saturate(168%)`，
邊緣折射以 `::before` 的漸層描邊配 `mask-composite: exclude` 做成 1px 的高光框。
深淺色各一組 `--glass-*` 變數。`prefers-reduced-motion` 時關掉位移與轉場。

## 後續需求：預設狀態不要有垂直捲軸

改回垂直排列時，`panelCardHeight` 與 `panelTopChrome` 是我從 CSS 推算的，結果偏差 22 px，
預設狀態就出現捲軸。改成用 CDP 在真實視窗實測。

### 量法

以 `dist/qa/preview.cjs` 擴充出的四來源合成資料開預覽（不觸及帳號資料），
用 Edge 的 `--remote-debugging-port` 連 CDP，以 Node 內建的 `WebSocket` 送 `Runtime.evaluate`
取各部位的 `getBoundingClientRect()`。沒有用到任何第三方套件。

先用 `--headless=new` 量內容，再開一個真實的 `--app` 視窗量視窗外框 ——
這一步不能省：headless 沒有標題列，而且真實視窗的內容寬度是視窗寬減 15（左右邊框），
header 在那個寬度下會折成兩行，比 headless 的 236 寬多出 13 px。

### 實測值（125% 縮放）

| 部位 | 高度 |
| --- | --- |
| 面板 header | 43.2（222 px 寬時折兩行） |
| 一般卡片 | 120.2 |
| Cursor 卡片 | 158.8（多 38.6） |
| footer | 38.6 |
| 面板內容總高 | 655.1 |
| 視窗標題列 + 上下邊框 | 36～38 |
| 左右邊框 | 15 |

常數因此改為 `panelCardHeight` 121、`panelCursorPools` 39，並把 `panelTopChrome` 拆成
`panelPageChrome`（112）、`panelWindowChrome`（38）與 `panelHeightSlack`（4）。
四個來源含 Cursor 為 236 × 701，以真實視窗確認 `overflows` 為 false、`scrollbar` 為 0。

### footer 的行數原本會隨主機名稱變動

量的時候發現 footer 的行數不是固定的：主機名稱一長就從兩行變三行，
視窗高度鎖定的情況下捲軸又會回來。`flex-wrap` 是用縮小前的 flex base size 決定換行，
所以只加 `overflow: hidden` 沒有用 —— 要把主機名稱的 `flex-basis` 設成 0，
它才不會參與換行判定，隱私說明則用 `flex: 1 0 100%` 固定自己一行。
以 2、15、63 字元的主機名稱驗過，footer 都是 38.78，面板總高不變。

`TestDefaultPanelFitsWithoutScrollbar` 把實測的內容高度寫進測試，
之後動到版面常數而沒有重新量的話會被擋下來。

## 後續需求：從面板空白處拖曳視窗

使用者要「隱藏瀏覽器標題列，並在內容空白處按住就能拖動視窗」。
規劃後先做風險最低的一半：保留標題列，加上空白處拖曳。

### 標題列拿不掉：已實測證實

`--app` 模式的標題列不是 DWM 畫的，是 Chromium 用 `WM_NCCALCSIZE` 把非工作區縮到零後
自己畫在 client area 裡面。以實驗程式對真實 Edge app 視窗拿掉 `WS_CAPTION` 後量測：

```
改前 style=0x16CF0000 WS_CAPTION=true  視窗高=702 client高=694 非工作區高=8
改後 style=0x160F0000 WS_CAPTION=false 視窗高=702 client高=695 非工作區高=7
```

client 高度只變了 1 px，非工作區本來就只有 8 px 的邊框 —— 那 38 px 的標題列整個在 client
area 內。**Win32 樣式位對它沒有作用**，這條路確定不通，不是「可能不通」。

唯一能真正移除標題列的是 PWA 搭配 `display_override: window-controls-overlay`，
但 PWA 的身分綁 `start_url`，而預設是隨機埠，每次啟動網址都不同，PWA 身分會壞掉。
要走這條必須先固定埠並加上安裝流程，已向使用者說明，尚未決定。

### 實作

頁面在空白處 `mousedown` 時 POST `/api/window/drag` 一次，之後每一幀的移動由 Go 端完成：
開一條 goroutine 以 8 ms 為間隔讀 `GetCursorPos`，用 `SetWindowPos`
（`HWND_TOPMOST`、`SWP_NOSIZE|SWP_NOACTIVATE`）把視窗移到「原點加游標位移」，
直到 `GetAsyncKeyState(VK_LBUTTON)` 顯示放開。

每個 `mousemove` 打一次 HTTP 是跟不上手感的，所以只送「開始」這一個訊號。
拖曳沒有放進 `LockPanelWindows` 的迴圈，因為那個迴圈每 10 秒會跑一次最長 5 秒的
PowerShell 查 PID，拖曳請求剛好落在那段就會卡住。

分層照既有慣例：`controller` 定義 `PanelWindow` 介面，`desktop` 實作 `PanelDragger`，
`app` 注入 —— `internal/architecture/dependencies_test.go` 不允許 controller 認識 desktop。
非 Windows 平台用 `window_drag_other.go` 的 no-op。

### 安全邊界

只搬 `LockPanelWindows` 已經比對過 PID 與視窗標題、確認是我們自己面板的視窗
（`publishPanelWindows` 發佈的清單），不會因為游標剛好在某個視窗上就去搬它。
`-no-browser` 時清單是空的，拖曳自動變成空操作。
端點跟其他資料 API 一樣走 `guard`，需要本機連線與 token。

### 驗證

以實驗程式對真實 Edge app 視窗跑與 `BeginPanelDrag` 完全相同的 `SetWindowPos` 呼叫：

```
位移=(160,80) 預期=(160,80)  尺寸不變=true  焦點未被搶走=true
負座標 位置=(-60,40) 預期=(-60,40)
```

位移精確、`SWP_NOSIZE` 與 `SWP_NOACTIVATE` 都生效、左側第二螢幕的負座標也正常。
`TestWindowDragIsGuardedAndOptional` 涵蓋驗證、非 POST、未注入視窗三種情況。

**按住拖曳的完整手感需要人操作滑鼠，無法自動化，仍待使用者實機確認。**

## 後續需求：關閉與最小化按鈕，以及 PWA 路線的評估

### 隱藏標題列：PWA 路線經實測評估後決定不做

接續上一節的結論（Win32 拿不掉標題列），實測了 PWA + `window-controls-overlay`：

1. **`--app=` 不吃 WCO。** 以帶 `display_override: ["window-controls-overlay"]` 的 manifest
   開 `--app=` 視窗，`navigator.windowControlsOverlay.visible` 為 `false`、
   `display-mode` 是 `standalone`、標題列仍佔 38 px。manifest 的 display 模式只對
   **已安裝**的 web app 生效。
2. **無法自動安裝。** Edge 153.0.4234.32 沒有 CDP 的 `PWA` 網域，
   `PWA.install` / `getOsAppState` / `launch` 全部回 `wasn't found`，
   也沒有可用的安裝 CLI 開關。

3. **最關鍵的一點：PWA 會毀掉單一執行檔的散布方式。** 使用者提出「分享給其他人時不能只用
   一個執行檔嗎」，這正是決定性的問題。走 PWA 後，每個拿到執行檔的人都必須：
   先看到一個有網址列的瀏覽器視窗、自己找到安裝鍵、通過一次安裝對話框；
   而且埠必須固定，在別人機器上可能已被占用；Edge profile 重置、手動移除應用程式、
   改用 Chrome 都要重裝。目前是雙擊執行檔就開、埠隨機不會相撞、複製到別台機器就能跑。

實際架設探測環境的過程本身也是證據：三次失敗（背景行程被收掉兩次、探測伺服器
沒有處理 `ui.html` 會請求的 `robot-icon.png` 而整個掛掉一次），而這還是在完全可控的
開發機上。要讓每個使用者順利走完安裝流程是另一個等級的可靠度問題。

除此之外還要：固定埠（PWA 身分綁 `start_url`，隨機埠每次啟動都是不同的 app）、
Go 端自行計算 Chromium 的 app id 才能用 `--app-id` 啟動，以及安裝被移除時的退路。
而「裝好之後標題列是否真的消失」這一步，在不請使用者點安裝對話框的情況下無法驗證。

結論：**不採用**。換來的只有少一條 38 px 的標題列，代價是散布方式與可靠度。
拖曳與自有的最小化／關閉按鈕做完之後，標題列已經不是必要的操作路徑，只是還佔著空間。

### 關閉與最小化：做了之後又整組移除

`controller.PanelWindow` 從只有 `BeginDrag` 擴成 `BeginDrag`、`Minimize`、`Close`，
三個端點共用 `windowCommand` 這個小包裝（同樣的 POST 檢查、同樣的 `ok: false` 退路）。
`desktop.PanelDragger` 改名為 `PanelController`。

做完之後使用者要求移除面板上的關閉與最小化按鈕，連同最上方的「AI 用量」標題文字一起拿掉，
並在確認後把沒有呼叫端的後端也整組刪除：`MinimizePanel` / `ClosePanel`、兩個端點、
`forEachPanel`，`PanelWindow` 介面縮回只有 `BeginDrag`，`windowCommand` 這個只剩一個呼叫端的
包裝也還原成 `handleWindowDrag`，`PanelController` 改回 `PanelDragger`，檔名改回 `window_drag_*.go`。
最終狀態沒有留下沒人呼叫的端點。

移除時只動內容區的 `<h1>`，`<title>AI 用量</title>` 必須保留 —— `LockPanelWindows`
是靠視窗標題比對才認得出面板，改掉會讓置頂、透明與尺寸鎖定全部失效。
header 原本就是一行、行高由 22 px 的圖示按鈕決定，所以移除後重新實測高度不變
（header 28.8、面板 640.7、236 × 687 仍然 `overflows: false`），視窗常數不需要調整。

關閉用 `PostMessage(WM_CLOSE)` 而不是自己結束程式：關掉視窗後 SSE 斷線，
背景程式沿用既有的「最後一個面板斷線約 8 秒後結束」，不另外開一條關閉路徑。

### header 塞不下標題加三顆按鈕

222 px 的內容寬度原本就讓 header 折成兩行。加上三顆按鈕會更糟，所以
重新掃描改成圖示按鈕，時鐘只留時間、「畫面更新於…」移到 `title`。
header 因此從 43.2 收成 28.8，面板總高 655.1 → 640.7，視窗 701 → 687，
反而比加按鈕之前更省空間。常數 `panelPageChrome` 隨之由 112 改為 98。

### 驗證

以實驗程式對真實 Edge app 視窗跑與 `MinimizePanel` / `ClosePanel` 相同的呼叫：

```
最小化 最小化狀態=true（預期 true）
還原   最小化狀態=false（預期 false）
關閉   視窗還在=false（預期 false）
```

尺寸重新實測：236 × 687 時 `overflows` 為 false、`scrollbar` 為 0，餘裕 9 px。
`TestWindowCommandsAreGuardedAndOptional` 涵蓋三個端點的驗證、非 POST 與未注入視窗。

實驗程式只比對視窗標題，正式的 `ClosePanel` 走 `panelHandles()`，

## 後續需求：拿掉展開按鈕，改成點卡片收合

使用者要求移除「詳細資訊 ＋／收合資訊 −」按鈕，改成在卡片上按左鍵展開或收合。

### 要跟拖曳區分開

卡片同時是拖曳把手也是開關，而拖完視窗放開滑鼠一樣會發出 `click`，
不處理的話每次搬完視窗都會順便把卡片展開。

判斷方式是比較 `mousedown` 與 `click` 的**螢幕座標**：拖曳時視窗跟著游標走，
所以 `clientX/Y` 在過程中不變，只有 `screenX/Y` 會變。位移超過 4 px 就當作拖曳，不切換。

### 無障礙

拿掉按鈕等於拿掉鍵盤操作路徑，所以卡片補上 `tabIndex=0`、`role="button"`、
`aria-controls`、`aria-expanded` 與 Enter／空白鍵處理，並加上 `:focus-visible` 外框。
展開後點卡片內的輸入框與按鈕不會收合（沿用 `DRAG_EXEMPT` 那組選擇器）。

### 高度連帶改變

移除按鈕後每張卡少了 22.4 px：卡片 120.2 → 97.8、Cursor 卡 158.8 → 136.4、
面板總高 640.7 → 551.1。`panelCardHeight` 由 121 改為 98，視窗 687 → 595，
實測 `overflows` 為 false、餘裕 7 px。`panelPageChrome`（98）與 `panelCursorPools`（39）不變。

## 檢視發現但未更動的項目

### [P2] `/api/stream` 改為固定每秒推送，`refresh_seconds` 不再影響面板更新

`internal/controller/server.go` 的 SSE ticker 由 `max(refresh_seconds, 1s)` 改成固定 1 秒。
好處是重置邊界的重查最多 1 秒就會出現在畫面上；代價是預設設定下推送頻率變成 3 倍，
而且 `render` 每次都會重建整列 DOM（展開狀態與編輯中表單有保護，其餘狀態不保留）。
倒數本身已改由前端 `setInterval` 每秒更新，不依賴推送頻率。

保留現狀，因為重查確實可能發生在兩次掃描之間；但這使 `refresh_seconds` 的語意
只剩「掃描間隔」，與 README 既有說明不完全一致，已在專案記憶中寫明。
若要兩者兼顧，較乾淨的作法是維持設定間隔，並在 `RefreshDueQuotas` 成功時主動喚醒 SSE。

### [P3] Windows 視窗樣式的成功訊息可能重複

`window_lock_windows.go` 的失敗訊息用 `failed[hwnd]` 閂住只印一次，成功訊息卻依
`configured[hwnd]` 的轉態決定；若瀏覽器還原樣式導致狀態來回切換，成功訊息會再印一次。
不影響功能。
